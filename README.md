# Kitty Chrome

Flatpak packaging for [Kitty Chrome](https://github.com/kreed/kitty) — the kitty
terminal with compact native GTK4 window chrome, running its terminal children
on the host rather than inside the sandbox.

## Install

```sh
flatpak remote-add --user --if-not-exists kitty-chrome \
  https://kreed.github.io/io.github.kreed.KittyChrome/kitty-chrome.flatpakrepo
flatpak install --user kitty-chrome io.github.kreed.KittyChrome
```

The repo is a GPG-signed OSTree archive published to GitHub Pages by
`.github/workflows/flatpak.yml`. The public key travels inside the
`.flatpakrepo` file, so adding the remote and trusting the key are one step.

## What lives here

| Path | |
|---|---|
| `io.github.kreed.KittyChrome.json` | the manifest |
| `io.github.kreed.KittyChrome.Devel.json` | same, but building kitty from a local worktree |
| `io.github.kreed.KittyChrome.{metainfo.xml,desktop}` | AppStream metadata and launcher entry |
| `patches/kitty/` | the host-children changes, applied to kitty at build time |
| `src/` | `kitty-host-agent`, the host PTY bridge, the entry-point wrapper and the `host-bin` shims |

Three repos, one concern each:

- **[kreed/kitty](https://github.com/kreed/kitty)** — the window chrome changes, and nothing else.
- **[kreed/ptyxis](https://github.com/kreed/ptyxis)** — a mirror of upstream Ptyxis plus three
  agent patches. Only `ptyxis-agent` is built from it; it is what creates host PTYs.
- **this repo** — packaging, publishing, and the host-children plumbing.

## Why the host-children code is a patch and not upstream

`patches/kitty/0001-Run-terminal-children-on-the-host.patch` touches
`kitty/child.py`, `kitty/window.py`, `kitty_tests/child.py` and adds
`kitty/host_spawn.py`. It lives here rather than in kreed/kitty so that the
kitty fork's diff against upstream is *only* the chrome work and stays easy to
rebase.

The cost is that the patch needs refreshing whenever kreed/kitty rebases onto a
newer upstream and `child.py` drifts. The refresh loop:

```sh
cd ../kitty-hostpty                       # a worktree kept for exactly this
git am ../io.github.kreed.KittyChrome/patches/kitty/0001-*.patch
# fix conflicts, then:
git format-patch --no-signature --zero-commit -o ../io.github.kreed.KittyChrome/patches/kitty <base>..HEAD
```

`--zero-commit` keeps an unchanged patch byte-identical between regenerations.

## Developing

`io.github.kreed.KittyChrome.Devel.json` swaps the pinned kitty git source for
`{"type": "dir", "path": "../kitty-hostpty"}` and drops the patch entry, so the
dev loop and the patch-refresh loop are the same activity: hack in the worktree,
then regenerate the patch when you are happy.

```sh
flatpak run org.flatpak.Builder --force-clean --user --install-deps-from=flathub \
  --install build io.github.kreed.KittyChrome.Devel.json
```

CI asserts the two manifests differ in nothing but that one source list.

## How kitty gets updated

The manifest pins an exact `kreed/kitty` commit, so pushing to that repo ships
nothing by itself. `.github/workflows/update-kitty.yml` runs nightly, moves the
pin, **builds it**, and only commits if the build passed — and that commit is
what republishes. To skip the wait, dispatch a `kitty-updated` event at this
repo, or run the workflow by hand.

## The desktop entry

`io.github.kreed.KittyChrome.desktop` is our own, not kitty's. kitty's is
generated by `setup.py` (see `linux-package`) and hardcodes `Name=kitty`, which
disagrees with the metainfo's `Kitty Chrome` and makes the launcher entry read
"kitty". Ours carries kitty's `X-TerminalArg*` keys verbatim so it still works
as the system default terminal — diff it against `setup.py`'s template when
bumping the kitty pin.

## Sandbox holes

`--filesystem=host`, `--talk-name=org.freedesktop.Flatpak` and `--device=dri`
together amount to a sandbox escape, and Flathub would reject them. They are
load-bearing here: the entire point is that terminal children run on the host
via `flatpak-spawn --host`, so a terminal that could not reach the host would
have no reason to exist. This is not a Flathub submission and is not intended
to become one.
